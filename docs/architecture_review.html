VerdictThe engineering is good. The structure and the data are what limit it.

This is a more carefully built repository than most in its category. The risk math has been reviewed and corrected, the reasoning is written down where the code is, determinism is enforced by test, and the known gaps are tracked honestly in REVIEW_STATUS.md rather than glossed. That is rare and it should not be undersold.

The problems are not sloppiness. They are three structural decisions that have compounded, plus one hard external constraint:

  • The package has two identities. portfolio_agent/ is a proper package; src/ is a flat script-style package reached through a repo-root symlink. Seventeen runtime modules import through the flat path. This is why the project cannot be installed.
  • The backtest engine absorbed everything. 2,412 lines, 47 methods, one class — and the thinnest test coverage of any large module relative to its risk.
  • Configuration is one flat surface of 108 settings with no notion of which subsystem owns what. (The training slice of this is fixed on the current branch; the rest is not.)
  • There is exactly one data source, and it is adjusted daily OHLCV. Every ambition beyond price-and-volume technical signals is blocked on that, not on modelling.

The constraint that outranks everything else

The repo already names this as D9 and it is the correct call: the universe is a current snapshot with no point-in-time membership, so every cross-sectional backtest carries survivorship and selection bias simultaneously. No amount of architectural work changes that. The findings below are about making the platform buildable, testable and extensible — not about making its current numbers believable.

Part 1 · RegisterArchitecture findings

A1

The package cannot be installed — strategies fail to import outside the repo root

Critical

Built the wheel and installed it into a clean virtualenv outside the repo. It builds and installs cleanly, and then cannot load a single strategy. strategies/rule_based.py tries from src.risk, then from risk — and never the canonical from portfolio_agent.src.risk, which works. Because strategies/__init__.py imports the registry eagerly, this one chain takes down the registry, the backtester and the engine together.

$ pip install git+https://github.com/3dwag98/afa@<branch> # succeeds >>> from portfolio_agent.strategies.registry import get_available_strategies ModuleNotFoundError: No module named 'risk' 17 runtime modules import through the flat path 6 of them have no portfolio_agent.* import at all: src/indicators.py src/outcomes.py src/portfolio_optimizer.py src/regime.py src/storage.py src/universe.py

The root src -> portfolio_agent/src symlink makes this invisible during development: everything resolves as long as the process starts at the repo root. It also means the real intra-src dependency graph is invisible to any tool that resolves imports properly — static analysis, IDE navigation and dead-code detection all under-report.

FixPut portfolio_agent. first in every fallback chain (india_sac.py already does this correctly — copy that shape). Keep the flat fallbacks so script-style execution still works. Roughly a day, mechanical, and each file is independently verifiable by importing it from a scratch directory.
A2

config.yaml is not packaged, so an installed copy silently runs on different settings

Critical

The loader resolves config.yaml relative to the working directory, then to the repo root. In an installed package neither exists, so it loads nothing and every value falls back to its schema default — with no warning.

repo config.yaml universe_size: 4000 installed package universe_size: 10 (schema default) wheel contents: portfolio_agent/** — config.yaml is absent

Silence is what makes this critical rather than annoying. A run that quietly uses a 10-name universe instead of 4,000 produces results, charts and a report, all of which look normal.

FixShip a packaged default config, resolve it as the last fallback, and log at INFO which file was actually loaded. A run should always be able to answer "which config am I on".
A3

BacktestEngine is a 2,412-line class holding at least nine responsibilities

Critical

One class owns data loading, price lookup, mark-to-market, position lifecycle, tax lots, stop/target evaluation, signal generation, regime classification, parallel scoring, order execution, Kelly sizing, the circuit breaker, sector caps, covariance and the portfolio risk cap, delisting, online learning, and performance reporting.

src/backtest_engine.py 2,412 loc 47 methods 17 test mentions by comparison: src/risk.py 714 loc 145 test mentions

The consequences are already visible. Every new feature adds a method here, so the class grows monotonically. Nothing inside it can be tested without constructing a full engine, which is why coverage is thin exactly where the money moves. And the live path (src/orchestrator.py, 637 loc) re-implements a subset of the same logic — the drift between backtest and live that strategies/base.py was introduced to eliminate has reappeared one level down.

FixExtract collaborators the engine composes rather than contains: Portfolio (positions, tax lots, mark-to-market), OrderRouter (creation, execution, fills), RiskGate (Kelly, caps, breaker, sector), ExitPolicy (stops, targets, triggers). Each becomes independently testable, and the live orchestrator can then use them instead of paraphrasing them. Do this incrementally, one collaborator per PR, with the engine's public output pinned by a golden-file test first.
A4

Test coverage is inverted against risk

Major

1,273 tests is a strong suite, but the distribution does not follow consequence. Modules that decide what gets traded and what gets reported are the least covered.

ModuleLOCTest mentionsWhat it decides
cli.py8730Every entry point
src/backtest_reporting.py9563The numbers humans read

src/markov_regime.py7031Regime gating (unwired)

The CLI at zero is the sharpest: it is the only surface a user touches, and it is the one place with no test at all. Three of the bugs found while building the current branch were in exactly this shape of code — plumbing that looked obviously correct.

FixSmoke-test every CLI subcommand with --help and one synthetic-data invocation; golden-file the report writer; give the two cross-sectional strategies the treatment rule_based already has.
A5

Substantial modules are built, tested and never switched on

Major

By the repo's own tracking: the Markov regime model is "done as a module; not switched on"; sleeve_weights exists but the orchestrator does not use it; the rank composite is opt-in; the portfolio optimizer sits on top of per-trade sizing rather than replacing it.

That is roughly 1,400 lines of maintained, imported, never-executed code. Each one is a decision deferred — and a deferred decision in a live trading system is a fork in behaviour that nobody has had to defend.

FixFor each, either switch it on behind a default-on config flag with a documented before/after comparison, or move it to an experimental/ namespace that is explicitly not part of the supported surface. The middle state is the expensive one.
A6

Configuration is one flat 108-setting surface with no ownership

Major

Ten sections, 108 leaf settings, 330 lines of YAML — and no mechanism saying which subsystem may read what. Any module can reach any setting, so the config object is a global namespace and changing a default requires reading the whole repo to know who is affected.

The training slice of this is fixed on the current branch: each trainer declares a pydantic schema with extra="forbid", so a misaimed setting is a startup error naming the alternatives. That pattern is the right one and it has not been applied to risk, simulation, compliance or execution.

FixExtend the per-subsystem schema pattern outward. The test to aim for: given a setting name, the code should be able to say which components read it — enforceable, not just documented.
A7

Two reinforcement-learning implementations with no stated relationship

Moderate

src/rl.py (499 loc) learns a portfolio-level exposure decision. training/trainers/sac.py (717 loc) learns per-name allocation. Both are defensible and they solve different problems — but nothing in either file says so, they share no abstractions, and a reader arriving at one has no way to know the other exists.

FixCheap: cross-reference the docstrings and state the division (exposure vs. allocation) in one place. If they are ever meant to compose — exposure scaling allocation — that is a design decision worth making explicitly rather than by accident.
A8

The sector map does not ship, and unmapped names silently weaken the cap

Moderate

src/sectors.py loads data/sector_map.csv. That file is not in the repository, and data/ contains only a ticker list and the parquet cache. The module reasons carefully about how to treat unmapped tickers — but the default state of a fresh clone is that every ticker is unmapped, so the concentration control that exists to stop a ten-name portfolio being one economic bet is inert until someone sources a file nobody tells them to source.

FixShip a sector map for the NSE 500, or derive one at ingest time and cache it. Failing that, log a warning at startup when coverage is below a threshold — silence is the wrong default for a disabled risk control.
A9

No workflow ties train → backtest → deploy into one traceable object

Moderate

Training writes a checkpoint. Backtesting reads it by filename convention. Nothing records that this backtest used that checkpoint trained on that universe with those settings. The universe fingerprint added on the current branch is the first piece of this, and it currently stops at the checkpoint.

FixA run manifest: one JSON per experiment carrying config hash, universe fingerprint, checkpoint hash, code revision and results. It makes "which model produced this report" answerable, and is the precondition for any honest live/paper comparison.

Part 2 · ErgonomicsMaking it pluggable and pleasant to use

Extension points are good; the workflow between them is the gap. Adding a strategy today means touching four files and reading a 950-line guide. Once added, taking it from idea to judged result is still a manual sequence of CLI calls with no record tying them together.

What already works and should be preserved

Four registries — features, model architectures, strategies, and now training procedures — all sharing one idiom. That consistency is the platform's best structural asset. BaseStrategy is a genuinely well-drawn interface: one contract serving live and backtest identically, with requires_full_batch and supports_gpu_batch capturing real distinctions rather than implementation detail.

The five gaps, in the order I would close them

GapTodayShould be
Registration is manual Edit strategies/registry.py, add an import, add a call Entry-point discovery, so a strategy in a separate package registers on install — the difference between "extensible" and "forkable"
No scaffold Copy an existing strategy, read the guide portfolio-agent new-strategy my_idea emitting class, YAML, test and registration
No contract test Each strategy's tests are hand-written A shared conformance suite every registered strategy runs automatically: lag-safety, NaN handling, determinism, empty-universe behaviour
No single command train, then backtest, then read a spreadsheet portfolio-agent evaluate --strategy X — train, walk-forward, backtest, report, one manifest
Excel is the only report 956-line writer, 3 test mentions Structured results object; Excel becomes one renderer among several (HTML, JSON, notebook)

The one that pays for itself first

The conformance suite. Lag-safety in particular should not be a per-strategy discipline — it should be a property the framework verifies for every registered strategy automatically, by feeding it a signal built from future data and asserting the backtest cannot profit from it. That single test class prevents the most expensive category of error in this domain, permanently, for every strategy anyone ever adds.

Part 3 · DataIs the data sufficient?

No — and this is the binding constraint. The platform ingests one thing: adjusted daily OHLCV for ~2,400 NSE/BSE symbols over about five years. Everything it can currently know is a function of price and volume.

That supports technical and cross-sectional price-based signals competently. It cannot support value, quality, growth, size, earnings revisions, flows, positioning, or genuine capacity modelling — not because the models are missing, but because the inputs are.

Part 4 · AmbitionWhat best-in-class would require

Taking "best in class for Indian markets" seriously means three things the platform does not yet have: a bitemporal data layer, a validation protocol built for overlapping financial labels, and an execution model that reflects how Indian equities actually trade.

The data layer becomes the product

Not a parquet cache — a store with as-of semantics, where every fact carries both the date it describes and the date it became known. Quarterly results are the clearest case: a result published on 15 May describing the quarter to 31 March must be invisible to any query dated 14 May. Without bitemporality this class of leak is undetectable by inspection, and it inflates exactly the factors people most want to add.

Validation has to assume overlapping labels

Predicting a 5-day forward return from daily observations means consecutive training samples share four days of outcome. Standard cross-validation leaks across that overlap and reports a skill that does not exist. The fixes are known and mechanical — purging and embargoing around the test fold, combinatorial purged CV for a distribution of outcomes rather than one number. The platform already has the harder half of this: PSR, DSR, PBO and a deduplicated trial log. Purged CV is the missing complement.

Models, in the order the evidence supports

  • Gradient-boosted trees on cross-sectional ranks first. On tabular panel data at this sample size they typically beat sequence networks, train in seconds, and are far easier to attribute. The LSTM is the more interesting model and the less appropriate default.
  • Residual momentum — momentum on returns orthogonalized to market and sector — directly addresses the concentration problem A8 describes, at the signal level rather than as a cap bolted on afterwards.
  • Seed ensembling before architecture search. Averaging five seeds of one model reliably buys more out-of-sample stability than finding a better single architecture, and costs nothing but compute.
  • Conformal prediction alongside isotonic calibration. Isotonic gives a calibrated point probability; conformal gives an interval with coverage guarantees that hold without distributional assumptions. Position sizing consumes uncertainty, so the interval is the more useful object.
  • Latent factor models (IPCA, conditional autoencoders) last. High ceiling, and they need the fundamental data above to be worth attempting.

Execution modelling that matches the venue

Flat basis-point costs are the placeholder every backtest starts with and few replace. For Indian equities specifically: participation-rate limits against actual traded volume, square-root market impact, circuit-band awareness so untradeable sessions are skipped rather than filled, and separate treatment of the overnight gap — which is where a large share of the move happens, and which is precisely what invalidates a stop-based risk model. The repo already flags this last one as partly done.

Part 5 · SequenceWhat I would do, in order

1–2 wks

Make it installable and testable

A1, A2, and the CLI half of A4. Cheap, mechanical, unblocks everything else including distribution and any notebook that wants to import the framework.

2–4 wks

Fix the data floor

Point-in-time index membership, a shipped sector map, delivery percentage. This is D9 and A8, and it is what converts every existing backtest number from decorative to interpretable.

Do this before any modelling work. Improving a model measured on a biased sample tells you nothing about the model.

3–6 wks

Decompose the engine, add the conformance suite

A3 and the rest of A4. Golden-file the current output first, then extract one collaborator per PR. Land the lag-safety conformance test early — it protects every strategy added afterwards.

2–3 wks

Close the workflow loop

A9 plus the ergonomics table: run manifests, evaluate as one command, entry-point discovery, a scaffold generator. This is what makes the platform pleasant rather than merely capable.

Ongoing

Then, and only then, the modelling ambition

Purged CV, gradient boosting, residual momentum, seed ensembling, conformal intervals. Each is a contained piece of work once the three above are done — and each is close to unmeasurable until they are.

  • Resolve A5 as you go: switch each dormant module on with a documented comparison, or move it to experimental/.
  • F&O and flows data when the bitemporal store exists to hold them properly.

The ordering principle

Every phase above is sequenced so that the work done in it can be measured by the time it lands. The most common failure mode for a platform at this stage is adding models before fixing the sample they are judged on — which produces months of work and no way to tell whether any of it helped.
